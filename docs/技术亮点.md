## 一、能扛住追问的亮点（建议写 4 条）

### 1. 库存中心：DB 条件扣减兜底 + Redis/Lua 前置快检 + 流水幂等回滚

**代码位置**：`StockServiceImpl`、`ProductMapper.deductStock/restoreStock`、`StockLogMapper.insertIgnore`、`stock_log` 表

**讲法**：商品库存以 `product.stock` 为唯一事实源，扣减用一条带条件的更新
`update product set stock = stock - ? where id = ? and stock >= ?`，影响行数为 0 就是库存不足——
这一条 SQL 本身就保证了不超卖，而且和订单写在同一个事务里，不需要补偿。
Redis 只承担两件事：库存读缓存（列表/详情展示）和下单前的 Lua 快检（读-比较原子化），
让明显不足的请求在开事务之前就被拒掉；快检判定不足时会回源 DB 复核一次，避免脏缓存误拒。
每次扣减/回滚都写 `stock_log`，回滚用 `insert ignore` + 唯一键 `(order_id, product_id, type)` 判重。

**追问与答法**
- 为什么不让 Redis 直接扣库存？→ 那样要额外处理「Redis 扣了 DB 失败」「Redis 重启丢数据」「Redis 与 DB 对账」三类一致性问题；用在秒杀这类场景才划算，普通下单 DB 条件更新足够。
- 组合商品怎么扣？→ 按 `bundle_item` 拆解到单品，销量 × 份数累加后再扣。
- 回滚会不会重复？→ 唯一键 + `insert ignore` 返回 0 即视为已回滚，用户取消和定时任务同时关单也只回滚一次。
- 还能怎么优化？→ 热点商品把库存全放 Redis + 异步落库 + 定时对账（可说明这是下一步）。

**边界**：库存是单仓、单品粒度，没有批次/效期/多仓调拨。

### 2. 下单幂等：客户端令牌 + 唯一索引

**代码位置**：`OrderServiceImpl.submitOrder`、`trade_order.idempotent_token` + `uk_idempotent_token`

**讲法**：客户端进入结算页生成一个 `idempotentToken`，随提交一起带上；服务端先按令牌查订单，
命中就直接返回同一笔订单（网络重试、用户连点都不会多下单）；数据库唯一索引兜底并发，
两个请求同时到达时只有一个能插入成功，另一个收到「请勿重复提交订单」。
支付接口同样做了幂等：已支付的订单重复调用直接返回，不会重复推送新单。

**追问与答法**
- token 为什么放数据库不放 Redis？→ 令牌要和订单在同一事务里落库，放 Redis 会出现「订单没建成但 token 已占用」的不一致。
- 重试返回什么？→ 返回原来那笔订单的 `OrderSubmitVO`，前端表现成"下单成功"，用户不会重复付款。

### 3. 订单状态机 + 条件更新的并发控制

**代码位置**：`OrderServiceImpl`（confirm / rejection / delivery / complete / cancel / pay）、`OrderTask`

**讲法**：6 个状态驱动全流程，**所有跃迁都是条件更新**：
`update trade_order set status = ? where id = ? and status = ?`，影响行数为 0 说明状态被别人改过，
抛「订单状态已变更，请刷新后重试」。两个店员同时点「接单」只会有一个成功；
定时任务只负责扫候选单，关单/完结逻辑下沉到 Service 的事务方法，保证「改状态 + 回滚库存」同一事务。

**追问与答法**
- 为什么不用乐观锁 `@Version`？→ 单表按状态流转，条件更新比 version 更直观，也不用改实体。
- 怎么验证的？→ 两个并发请求打同一个订单的接单接口，一个返回成功、一个返回状态已变更，最终状态只有一次跃迁。

### 4. 缓存：两套策略 + 库存不进列表缓存

**代码位置**：`ProductServiceImpl.listWithSpec/cleanCache`、`BundleController`（`@Cacheable`/`@CacheEvict`）

**讲法**：商品列表按类目维度缓存（`freshmart:product:category:{id}`），写后按前缀失效；
组合商品用 Spring Cache 注解；**库存不放进商品列表缓存**——它随每笔订单变化，
放进去立刻变脏，所以缓存只存商品静态信息，返回前再用 `StockService.getStock` 补实时库存。

**追问与答法**
- 一致性？→ 先写库后删缓存，接受短暂不一致，下次读回源。
- 穿透/击穿/雪崩？→ 目前没做，可加空值缓存、互斥锁、过期时间打散。
- `keys` 的问题？→ O(N) 且阻塞 Redis 主线程，生产改精确删除或 `SCAN`。

| 会员端小程序 | 自己写的 8 页原生小程序，统一请求封装（自动带 token、401 清理） | 端到端联调 |

## 四、已验证的证据（面试可以直接说"我测过"）

| 场景 | 实测结果 |
| --- | --- |
| 正常下单 2 件 | 库存 100 → 98，订单落库，库存流水 type=1 |
| 同一幂等令牌重复提交 | 返回同一订单 id，库存不变，令牌只落 1 条 |
| 库存不足（3 件库存买 5 件） | 拒绝并提示「商品库存不足：阳光玫瑰葡萄 500g」，不产生订单、不扣库存 |
| 取消订单 | 库存 97 → 100，流水 type=1、type=2 各一条 |
| 二次取消 | 返回「订单状态已变更，请刷新后重试」 |
| 并发接单（同一订单两个请求） | 一个成功、一个被拒，最终状态只跃迁一次 |
| 重复支付 | 幂等返回成功，订单状态不变、不重复推送 |
| 超时关单（定时任务） | 20 分钟前未支付的订单被关掉，状态 6、库存回滚、原因写入 |

## 五、30 秒版本（背这段）

> 我做的是一个线上生鲜超市系统，会员小程序下单、门店后台履约。后端 Spring Boot + MyBatis-Plus + MySQL + Redis，71 个接口、12 张表。
> 订单是 6 个状态的状态机，所有跃迁都用条件更新，所以并发接单只有一个人能抢到；下单用事务保证订单、明细、扣库存、清购物车原子；超时未支付的订单由定时任务关掉并回滚库存。
> 库存以数据库为事实源，用 `stock >= ?` 的条件更新保证不超卖，Redis + Lua 只做下单前快检和展示缓存；每次扣减/回滚都记流水，回滚靠唯一键幂等，取消和超时同时发生也只回滚一次。
> 下单幂等用客户端令牌 + 数据库唯一索引，网络重试不会重复建单；另外商品列表按类目缓存、支付后用 WebSocket 推新单、报表用聚合 SQL + POI 导出 30 天日报。
