# 面试追问与答题要点

> 用法：先用 30 秒讲完「介绍」，再按面试官的兴趣点展开。每题都给「项目现状 → 这么做/没这么做的原因 → 如果继续怎么改」，这是面试官真正想听的三段式。

## 1. 用 30 秒介绍一下这个项目

> 这是一个线上生鲜超市系统：会员在小程序里按类目逛商品、加购物车、下单支付；门店后台接单、拣货、配送；同时提供销售额、完成率、动销 Top10 和日报导出。
> 后端是 Spring Boot 2.7 + MyBatis-Plus + MySQL + Redis 的单体应用，Maven 三模块分层，71 个接口，按运营端和会员端两组用 JWT 隔离鉴权。
> 技术上重点做了两块：订单状态机的并发控制和库存的防超卖。

## 2. 为什么做「门店 30 分钟达」而不是普通商城？

> 普通商城的主链路是「下单 → 发货 → 物流」，核心矛盾在商品和库存；线上超市的核心矛盾是**配送时效**：订单要在 30 分钟内从门店到家。
> 所以我把建模重点放在**订单的生命周期**上：状态机、超时兜底、库存占用与释放，这些才是这类系统真正的难点。

## 3. 订单状态机怎么设计的？并发接单会不会重复？

**现状**：6 个状态（待支付 / 待拣货 / 已接单 / 配送中 / 已完成 / 已取消），**所有跃迁都是条件更新**：

```sql
update trade_order set status = 3 where id = ? and status = 2
```

影响行数为 0 说明状态已被别人改过，直接抛「订单状态已变更，请刷新后重试」。

**效果**：两个店员同时点「接单」，只有一个返回成功，另一个收到明确提示，不会出现两个人"都接单成功、重复通知"。

**验证**：并发打同一个订单的接单接口，结果是一个 1、一个 0，最终状态只跃迁一次。

**如果继续改**：可以用状态机流转表把「允许的跃迁」配置化，避免状态判断散落在各个方法里。

## 4. 库存怎么防超卖？

**现状**：库存以 `product.stock` 为唯一事实源，扣减是带条件的更新：

```sql
update product set stock = stock - ? where id = ? and stock >= ?
```

影响行数 0 就是库存不足。这条 SQL 与订单写入在同一个事务里，所以不会超卖，也不存在"扣了库存订单没建成"的补偿问题。

Redis 只做两件事：库存读缓存（列表/详情展示）和下单前的 **Lua 快检**——`get` 与比较在脚本里原子执行，明显不足的请求在开事务前就被拒掉，减少无谓的事务开销；快检判定不足时还会回源 DB 复核一次，避免缓存脏读导致误拒。

**为什么不直接把库存扣在 Redis 里**：
> 那样要额外处理三件事——Redis 扣成功但 DB 落单失败怎么补、Redis 重启丢数据怎么恢复、Redis 与 DB 怎么对账。只有在秒杀这种读多写极端的场景下才值得，普通下单用 DB 条件更新更稳。

**边界**：库存是单仓、单品粒度，没有批次和效期；组合商品按 `bundle_item` 拆解到单品扣减。

## 5. 取消订单怎么回滚库存？会不会重复回滚？

**现状**：用户取消、商家拒单、超时关单都会回滚库存。每次扣减/回滚都写 `stock_log`，回滚前先插一条 `type=2` 的流水，靠唯一键 `(order_id, product_id, type)` 判重——`insert ignore` 返回 0 就说明这笔已经回滚过，直接跳过。

**为什么这样设计**：取消有多个入口（用户点取消、店员拒单、定时任务超时关单），它们可能同时发生；用"流水唯一键"而不是"先查再做"，天然幂等，也不用加锁。

**验证**：同一订单取消两次，第二次返回「订单状态已变更」；超时关单任务跑完后库存精确回到原值，流水里 `type=1` 和 `type=2` 各一条。

## 6. 下单幂等怎么做的？

**现状**：客户端进入结算页生成 `idempotentToken`，提交时带上。
1. 服务端先按令牌查订单，命中就直接返回**同一笔订单**（网络重试、手抖连点都不会多下单）；
2. 数据库对 `trade_order.idempotent_token` 建唯一索引兜底并发——两个请求同时到达时只有一个能插入成功；
3. 支付接口也幂等：已支付的订单重复调用直接返回，不重复推新单。

**为什么令牌要落库**：令牌必须和订单在同一个事务里生效，放 Redis 会出现"token 占了但订单没建成"的不一致。

## 7. 下单为什么要事务？事务边界在哪？

> `submitOrder` 里做了四件事：写 `trade_order`、批量写 `trade_order_item`、条件扣减库存 + 写流水、清空 `cart`。
> 四张表必须原子：明细失败而库存已扣、或者购物车清了却没建成订单，都是事故。所以整个方法加 `@Transactional`。
> 定时任务里的「关单 + 回滚库存」也下沉到 Service 的 `@Transactional` 方法，保证两者同成功同失败。

## 8. Redis 缓存怎么用的？一致性怎么保证？

**现状**：商品列表按类目缓存，key 是 `freshmart:product:category:{categoryId}`，读时先查 Redis、未命中查库回填；商品和类目写操作后按前缀 `freshmart:product:*` 批量删 key。组合商品列表用 Spring Cache 注解。

**库存为什么不进缓存**：库存随每笔订单变，放进商品列表缓存会立刻变脏；所以缓存只存商品静态信息，返回前用 `StockService.getStock` 补实时库存（Redis 优先、未命中回源 DB）。

**已知问题**：`keys` 是 O(N) 命令且阻塞 Redis 主线程，key 多了就是事故。改进：按类目精确删除，或 `SCAN` 游标分批删。

## 9. 如果 Redis 挂了，还能下单吗？

> 不能，快速失败会抛连接异常。这是明确取舍：库存的正确性由 DB 保证，但快检和缓存依赖 Redis。
> 改进方案：缓存层加降级——捕获异常后跳过快检直接走 DB 条件扣减（正确性不受影响），并打点告警；商品列表降级直查 DB。

## 10. WebSocket 在什么场景用？集群下有什么问题？

**现状**：支付成功后广播「新单提醒」，会员催单时广播催单消息，门店端不用轮询。实现是单机 `Map<sid, Session>` 群发。

**集群问题**：多实例各自持有自己的 Session 表，A 实例的连接收不到 B 实例的消息。
**怎么改**：把广播抽成消息总线（Redis Pub/Sub 或 MQ），每个实例收到后只推给自己持有的会话。

## 11. 定时任务为什么这么设计？多实例会重复执行吗？

**现状**：`@Scheduled` 两个任务——每分钟扫「超过 15 分钟未支付」的订单，每天凌晨处理「配送中超过 60 分钟」的订单。任务只负责扫 ID，关单/完结逻辑在 Service 的事务方法里，且用条件更新，所以重复执行是安全的。

**多实例问题**：会重复扫，但重复执行不会产生错误结果（条件更新 + 库存回滚幂等）。
**怎么改**：加分布式锁或换 XXL-JOB；超时关单更适合延迟消息（RabbitMQ 死信 / RocketMQ 延迟级别）替代轮询。

## 12. 报表的 SQL 会不会慢？怎么优化？

**现状**：实时聚合，`sum(amount)` / `count(*)` 带 `status` 与 `order_time` 区间条件；动销 Top10 是手写 `@Select` 做 join + group by + limit。

**优化路径**：
1. 联合索引 `(status, order_time)`；
2. 按天离线汇总到统计表（把 O(订单数) 降到 O(天数)）；
3. 30 天明细导出改分页/游标读。

## 13. JWT 鉴权怎么做的？

**现状**：登录签发 JWT（运营端与会员端两套密钥），拦截器解析后把 id 放进 `BaseContext`（ThreadLocal），请求结束清理；token 有效期较长，没有刷新机制。

**问题**：无法主动踢人、无续期 → 短有效期 access token + refresh token；token 进 Redis 白名单/黑名单实现登出。

## 14. MyBatis-Plus 相比原生 MyBatis，你用了哪些能力？

> 1）`BaseMapper` 免写单表 CRUD；2）`LambdaQueryWrapper` / `LambdaUpdateWrapper` 类型安全地拼条件，
> **状态条件更新就是用 `LambdaUpdateWrapper` 拼的**；3）分页插件直接出 total；
> 4）`MetaObjectHandler` 自动填充创建/更新时间与操作人；5）`@TableName` 显式绑定表名。
> 复杂聚合（动销 Top10）和带条件的库存扣减还是手写 SQL——条件构造器表达不了 `stock >= ?` 这种原子语义。

## 15. 你觉得最难的地方 / 这个项目的不足？

**最难**：把「看起来是 CRUD 的下单」拆成三个真问题——订单状态怎么不被并发搞乱、库存怎么不超卖、取消/超时怎么幂等地把库存还回去。这三个问题在代码里各有一处落点（条件更新、`stock >= ?`、流水唯一键）。

**不足（主动说）**：
1. 单机 WebSocket、单机定时任务，没有水平扩展能力；
2. 支付是模拟的，缺支付回调幂等与对账；
3. 库存没有批次/效期和多仓，也没有定时对账任务；
4. 缓存异常的降级策略没做。

**下一步**：延迟消息替代轮询关单 → WebSocket 集群化 → 库存对账任务。
